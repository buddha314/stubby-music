## Context

A rack module today is defined in three places:

| Where | What it holds | Owner |
| --- | --- | --- |
| `assets/modules/<id>/asset.json` | panel: model, `module_kind`, ports with direction, knob ranges and taper, lights, lamp, display | art (written by `tools/blender/module_kit.py`) |
| `synth_modules::engine_kind` | `module_kind` string → `ModuleKind`, with hard-coded defaults | game |
| `rack.rs` `parts`, `knob_default`, `knob_target`, `internal`, `jack`, `is_output` | engine parts, defaults, knob → param, internal wiring, jack → port, direction | game |

The copies have drifted (volume gain 0.25 vs 0.7; a stale built-in envelope in
`volume/asset.json`). `rack.rs` also does the pure work of planning a rack's engine
patch (`modules`, `plan`, `Plan`) inside a Bevy file, so it can only be tested by
building an app. The recipes system already shows the pattern this change follows: a
Bevy-free core that owns rules data, validates it strictly, and is wrapped thinly by
the game (`stubby_recipes` / `bevy_stubby_recipes`).

## Goals / Non-Goals

**Goals:**
- One definition per module; adding a module whose engine parts exist is data only.
- Strict validation reporting every error, including drift against `asset.json`.
- Patch planning that is pure, Bevy-free and unit-tested.
- The burbler sounds exactly as it does today.

**Non-Goals:**
- New engine parts, or making `ModuleKind` itself data-driven. A new DSP part is still
  a `stubby_audio` change.
- Changing machine configurations (`configure` blocks), the rack screen, cables or the
  comb.
- Hot reloading definitions through `bevy_common_assets` (definitions are embedded at
  build time, as profiles are today; hot reload can follow).
- The module ID allocator (`add-module-asset-binding` 2.1).

## Decisions

### A sibling `module.json`, not more fields in `asset.json`
`asset.json` is regenerated by the Blender scripts and is art's file; engine behaviour
is game logic. A separate file keeps each owner in their own file, so a model
re-export can never erase wiring and a wiring change never touches art. The validator
joins the two by module ID and reports drift.
*Alternative:* add an `engine` block to `asset.json` and teach `module_kit.py` to
carry it through. Rejected: it couples every wiring edit to a Blender run.

### A new Bevy-free crate, `stubby_rack`
It holds the definition types, the loader and validator, the default-source enum and
the patch planner. It depends on `stubby_audio` (for `ModuleKind`, `Command`,
`PortRef`) and `serde`, never on Bevy, as `stubby_recipes` never does.
*Alternatives:* put it in `stubby_recipes` (rejected: recipes are about items and
crafting, not signal routing; it would make that crate depend on the audio engine), or
keep it as a module in `stubby_game` (rejected: the planner stays untestable without
Bevy, and the game crate is the one we are trying to shrink).

### Engine parts named by `ModuleKind` variant, parameters by port name
A part is `{ "part": "vca", "kind": "Vca" }`. `stubby_rack` owns one function that
turns a kind name plus parameter values into a `ModuleKind`, and a table of each
kind's ports (with direction) and parameters taken from `ModuleKind`'s documented
interface. Validation checks bindings against that table. This replaces both
`engine_kind` and `parts`.

Example, `assets/modules/volume/module.json`:

```json
{
  "id": "volume",
  "parts": [{ "part": "vca", "kind": "Vca" }],
  "internal": [],
  "jacks": {
    "trig": "vca.cv",
    "in": "vca.in",
    "out": "vca.out"
  },
  "knobs": {
    "gain": { "param": "vca.gain", "default": 0.25 }
  }
}
```

and `square_vco`'s FREQ knob: `{ "param": "vco.freq", "default": { "source": "lightning_bug_pitch" } }`.

### Jack direction comes from the panel only
`is_output` is deleted. Direction is read from `asset.json`'s `ports[].direction` and
validated against the bound engine port's direction, so it is stated once.

### Default sources are a closed enum
`machine_clock_bpm` and `lightning_bug_pitch` are the two world-dependent defaults in
use. The game supplies their values to the planner through a small context
(`DefaultContext { clock_bpm, bug_pitch_hz }`). Rows never hold expressions; a new
source is a rule change (AGENTS.md, "Rows never hold logic").

### Embedded at build time
Definitions are `include_str!`'d, as `synth_modules::PROFILES` is today, so the game
and the Jackdaw adapter read identical data. A test in `stubby_rack` loads every
shipped definition and cross-checks it against its `asset.json`.

## Risks / Trade-offs

- [`ModuleKind`'s port table in `stubby_rack` drifts from `stubby_audio`] → keep the
  table next to `ModuleKind` in `stubby_audio` as `ModuleKind::ports()` /
  `ModuleKind::params()`, so the engine states its own interface and `stubby_rack`
  only reads it.
- [Showcase behaviour changes: volume gain 0.7 → 0.25] → intended; called out as
  breaking in the proposal. If the showcase reads too quiet, change the one default.
- [Shared files: workspace `Cargo.toml`, `Cargo.lock`, `stubby_jackdaw/Cargo.toml`] →
  keep edits to one line each and update from `main` before the PR.
- [`stubby_jackdaw` compiles `stubby_game` by `#[path]`] → it must list `stubby_rack`
  as a dependency too; the `prefabs` test catches a miss.

## Migration Plan

1. Land `stubby_rack` with definitions and tests, unused.
2. Switch `rack.rs` to it, checking the burbler patches and sounds as before.
3. Switch `synth_modules.rs`, then delete the six functions and `engine_kind`.

Each step builds on its own; rollback is reverting the last step.

## Open Questions

- Should the clock lamp's `Clock` part default to the seeded tempo too, or keep a
  plain 120? (Proposed: a plain number until a machine uses it.)
- Saw and triangle VCOs have no engine part yet. Proposed: no `module.json` until they
  do, and validation allows a panel without a definition only when it is in no rack
  configuration.
