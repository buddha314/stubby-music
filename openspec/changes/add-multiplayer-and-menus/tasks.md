## 3. Shared world state (host decides, D4)
- [x] 3.1 Collecting and sources (lightning bugs, plants, mines) (claimed: Claude). A joined client's harvest is a request on `stubby_net::HostChannel`; the host checks reach (`HOST_REACH`) and availability, depletes the source in the world's `SourceLedger` (moved out of the player's inventory: depletion is the world's) and sends the yields to that client alone (`GrantHarvest`). Depleted sources replicate to everyone, late joiners included, and return on the host's clock. Mines are machine production: they run on every peer from the shared racks (3.5); their output reaching inventories is not yet the host's. Until 3.2, a client's inventory is its own: it checks for room before asking
- [x] 3.2 Inventory per player and shared storage, moves between them as host-checked requests (open question 1, settled) (claimed: Claude). The host keeps each remote player's `Pack` (inventory and recipe book), replicated to its owner alone and mirrored into its `PlayerInventory`; `SharedStorage` (48 boxes) replicates to everyone. Harvests, crafts and `StorageRequest`s from a joined client are the host's, by the single-player rules (`recipes_plugin::craft`, `StorageRequest::apply`); the client's recipes plugin stands aside (`DecidedElsewhere`), so nothing is applied twice. Tests: inventories private and host-kept, storage shared both ways with refusals, a craft made once from the host's pack. Storage became built barrels in 3.3 (the user's choice). **Not yet:** inventory changes made outside the recipes plugin (building, the rack, stream dismantling, goal deliveries) still change only a client's own copy until 3.3–3.5 (building and dismantling: done in 3.3)

- [x] 4.2 Clock following against lightyear's synchronized tick, so music tied to a location is in time for everyone; measure and report the drift (open question 4, settled) (claimed: Claude). Every machine clock derives from its engine's sample counter, so the engine gained a master offset (`Command::SetMasterOffset`, `bevy_stubby_audio::MasterOffset`). The host publishes its master beat against its tick (`HostBeat`, twice a second); a client projects it to now on lightyear's `RemoteTimeline` and shifts its offset when the smoothed error passes 15 ms (`multiplayer::music`), logging every correction and a report every 30 s. **Measured:** in-process (both clocks known exactly) 5.4 ms on a clean link and 4.5 ms over a 50 ms, 3 %-loss link; between two real game processes with real engines, +5 ms held for over a minute with no corrections, after up to about 120 ms off in the first ~10 s while the joining game loads its scene. Found: reading the timelines in PreUpdate, before the fixed steps take the frame's time, put the clocks a tick (about 22 ms) apart
