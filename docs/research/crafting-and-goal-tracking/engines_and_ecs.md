# Quest / objective / goal tracking: engines, tool vendors, ECS and Rust/Bevy

Scope: how quest/objective/task tracking is architected in Unreal (Lyra, plugins, achievements), Unity (Pixel Crushers), narrative tools (articy:draft, Yarn Spinner, ink), shipped-game talks (Horizon Zero Dawn, The Witcher 3), and the Rust/Bevy ecosystem. The aim is to inform a Bevy-free Rust core library used from a Bevy 0.20 game. Research date 2026-11-01. About 20 tool calls; several primary docs (Lyra source, Narrative official docs, Pixel Crushers manuals) could not be fetched. See the Gaps sections.

## Unreal: Lyra messaging, Gameplay Tags, quest plugins, achievements

### Takeaway
Unreal's idiom is a decoupled publish/subscribe bus. Channels are Gameplay Tags and payloads are structs; Lyra routes nearly everything through one generic "verb message" (verb tag, instigator, target, tag containers, magnitude). Quest plugins such as Narrative attach small task objects to graph nodes. Each task listens for game events and calls `AddProgress` toward a `Required Quantity`. Platform achievements reduce progress to a monotonic 0–100% float per achievement ID.

### Cited Findings
- The GameplayMessageSystem (introduced in UE 5.0) is a subsystem that lets "unconnected gameplay objects communicate" without references, delegates or knowledge of each other. It is publish/subscribe: a broadcaster sends a Message on a Channel without knowing who receives it, and a listener subscribes to a Channel with a callback taking (Channel, Message) — [Unreal Community Wiki: GameplayMessageSystem](https://unrealcommunity.wiki/gameplaymessagesystem-74b916)
- A Channel is a GameplayTag (hierarchical names are recommended), and a Message is any USTRUCT both sides agree on. Broadcasts are not network-replicated unless sent explicitly through RPCs — [Unreal Community Wiki](https://unrealcommunity.wiki/gameplaymessagesystem-74b916)
- Lyra uses one struct, `FLyraVerbMessage`, for almost all messages. Its fields are `Verb` (FGameplayTag), `Instigator` and `Target` (UObject), `InstigatorTags`, `TargetTags` and `ContextTags` (FGameplayTagContainer), and `Magnitude` (double, default 1.0), described as having "enough information data fields to encompass most common gameplay events" — [Unreal Community Wiki](https://unrealcommunity.wiki/gameplaymessagesystem-74b916)
- Lyra experience definitions carry the scoring rules: team deathmatch scores by kill count, control points by capture events — [Epic: Lyra sample docs (zh-cn, 5.0)](https://dev.epicgames.com/documentation/zh-cn/unreal-engine/lyra-sample-game-in-unreal-engine?application_version=5.0)
- In UE 5.4, Lyra's native tag declaration moved from an `FLyraGameplayTags` struct to a `LyraGameplayTags` namespace using `UE_DECLARE_GAMEPLAY_TAG_EXTERN`. This shows tags declared as compile-time constants in code alongside data-authored tags — [Zenn (JP)](https://zenn.dev/piteki/scraps/d887141836c3db)
- Narrative (Narrative Tales) plugin: a Quest contains task nodes in a Quest Graph. Each task node has a **Required Quantity** (for example 3 pumpkins) and a description. Tasks are Blueprint classes ("Narrative – Task"), and there is also a separate "Data Task" kind — [Versluis: Creating Custom Tasks for Quests in Narrative Tales (2025)](https://www.versluis.com/2025/08/creating-custom-tasks-for-quests-in-narrative-tales/)
- A Narrative task overrides `Begin Task`, binds to a game event (the example uses an inventory "On Add Item" dispatcher), filters it, and calls **Add Progress**, which "inform[s] our Quest about the quantity added". When the required quantity is reached, the graph moves to a "succeed quest" node. Tasks take arguments (an item-name string passed from the quest), so one task class serves many quests — [Versluis](https://www.versluis.com/2025/08/creating-custom-tasks-for-quests-in-narrative-tales/)
- A noted edge case: on begin, a task should count items the player *already has*. Otherwise it waits only for new events, even though the requirement may already be met — [Versluis](https://www.versluis.com/2025/08/creating-custom-tasks-for-quests-in-narrative-tales/)
- Narrative only searches folders listed in a configured "Quest Task Search Path" for task classes, for performance — [Versluis](https://www.versluis.com/2025/08/creating-custom-tasks-for-quests-in-narrative-tales/)
- The Quest Extension plugin (Marketplace) records world events over time as "Memories" and uses them to complete quests, for example a boss-kill memory satisfying "Kill the boss". This is an event-log model rather than a pure live-listener model — [Unreal Marketplace: Quest Extension listing](https://www.unrealengine.com/marketplace/content/c47dc67dda684ee6b3685c64c8008428)
- Fortnite's Verse API has `quest_objective` and `progress_quest_objective` types under a progression module. Search snippets describe counting toward a required total, "X / Y" display, and a progress-changed event, but the pages would not render for full detail — [Verse: progress_quest_objective](https://dev.epicgames.com/documentation/fortnite/verse-api/unrealenginedotcom/progression/progress_quest_objective), [Verse: quest_objective](https://dev.epicgames.com/documentation/fortnite/verse-api/unrealenginedotcom/progression/quest_objective)
- Online Subsystem Achievements: `WriteAchievements` takes an `FOnlineAchievementsWrite` (which wraps `FOnlineStats`), keyed by achievement ID with a float **0.0–100.0 completion percentage**. Progress is cumulative and can be partial. "Many services reject updates that do not raise a player's existing percentage", so read before writing. `QueryAchievements` and `GetCachedAchievement(s)` read per-player progress. Descriptions (`FOnlineAchievementDesc`) are shared across players and fetched separately. Achievement definitions are created in each platform's backend, not in the interface. `ResetAchievements` exists only in non-Shipping builds — [Epic: Online Subsystem Achievements Interface](https://dev.epicgames.com/documentation/en-us/unreal-engine/online-subsystem-achievements-interface-in-unreal-engine)

### Inferences
- Lyra's verb message maps directly to a plain Rust event: `struct GameEvent { verb: Tag, instigator: Option<EntityRef>, target: Option<EntityRef>, instigator_tags, target_tags, context_tags: TagSet, magnitude: f64 }`. A core library can match objectives against `(verb, target-tag filter, magnitude)` without knowing game types. Horizon's "verb + target + count" (below) is the same idea.
- Narrative's split of a graph node (structure plus Required Quantity) from a task (event filter plus AddProgress) suggests separating *what counts* (a filter predicate over events) from *how much is needed* (a target in the definition) and *how much is done* (per-save counter).
- The "items already held" edge case argues for objectives that can be evaluated against **state queries** (inventory count) as well as **event deltas** (item picked up). Otherwise an objective activated late misses prior progress.
- The achievements API shows two separations: definitions live in a backend, per-player progress is a number, and writes must be monotonic. That suggests a `max(old, new)` merge rule, which also makes repeated writes idempotent.

## Unity: Pixel Crushers Quest Machine / Dialogue System, ScriptableObject data

### Takeaway
Quest Machine is the most fully specified commercial data model found. Quests are graphs of typed nodes (Start / Condition / Passthrough / Success / Failure), each with a three-valued state (Inactive / Active / True). Condition sets combine with Any/All/Min, and conditions include counter thresholds, messages, timers, parent counts and other quests' states. Counters can be updated by messages or by data sync. Save data is a separate minimal state serializer, distinct from the authored quest asset.

### Cited Findings
- Quest Machine enums (API reference v1.2.75): **QuestState** = WaitingToStart, Active, Successful, Failed, Abandoned, Disabled. **QuestNodeState** = Inactive, Active ("waiting for conditions"), True ("conditions have been met"). **QuestNodeType** = Start, Success (sets quest successful on activation), Failure, Passthrough (immediately true), Condition (monitors success/failure conditions and activates destinations) — [Pixel Crushers Quest Machine API: namespace](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Conditions: abstract `QuestCondition`, `CounterQuestCondition` (counter reaches a value, with `CounterValueConditionMode` AtLeast/AtMost), `MessageQuestCondition` (a MessageSystem message is received), `TimerQuestCondition`, `ParentQuestCondition` (enough parent nodes are true, so joins in the DAG), and `QuestStateQuestCondition` / `QuestNodeStateQuestCondition` (cross-quest prerequisites). `QuestConditionSet` groups conditions with `ConditionCountMode` Any / All / Min — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Counters: `QuestCounter` holds an integer. `QuestCounterMessageEvent` changes a counter when a message arrives. `QuestCounterUpdateMode` is DataSync or Messages, so a counter is either pushed by events or synced from an external data source. `QuestCounterSetValueMode` controls whether listeners are notified — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Actions run when quests or nodes become active: `SetQuestStateQuestAction`, `SetQuestNodeStateQuestAction`, `GiveQuestToQuesterQuestAction`, `MessageQuestAction`, `UnityEventQuestAction`, and `SetCounterValueQuestAction`. `ActionRequirement` and `ActionEffect` describe preconditions and world-model effects, used by its procedural quest generator — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Save/load uses `QuestProxy` / `QuestNodeProxy` ("runtime-serializable proxies") and JSON save-data classes (`QuestNodeJsonSaveData`, `QuestCounterJsonSaveData`, `ConditionSetJsonSaveData`, `StaticQuestJsonSaveData`). `QuestStateSerializer` "serializes the minimum data needed for design-time quests" — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Journal and UI are separate: `QuestJournal`, `IQuestJournalUI`, and `QuestIndicatorState` (Offer, Talk, Interact, …, Custom0–9) — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Quest Machine ships its own message system, and counters and messages are optional. Custom conditions written by users appear in the editor like built-in ones — [Unity Discussions: Quest Machine release thread](https://discussions.unity.com/t/released-quest-machine-hand-written-and-procedurally-generated-quests/677637)
- In third-party integrations, quest/node state and counter values are read by **polling getters** that return snapshots, not subscriptions. A getter must re-run to refresh — [Opsive State Designer: Quest Machine integration](https://opsive.com/support/documentation/state-designer/integrations/quest-machine/), [Opsive Behavior Designer Pro integration](https://opsive.com/support/documentation/behavior-designer-pro/integrations/quest-machine/)
- Dialogue System for Unity (Pixel Crushers) stores quests as entries in a Quest/Items database table with Lua state. Conditions such as `CurrentQuestState("name") == "unassigned"` and scripts such as `SetQuestState("name","success")` are used; quests have both quest-level state and per-entry (objective) state — [iThome blog (zh-TW)](https://ithelp.ithome.com.tw/articles/10224888); [Opsive: Dialogue System integration](https://opsive.com/support/documentation/state-designer/integrations/dialogue-system/)
- Other Unity/Godot systems converge on the same shape. Game Creator tasks have inactive/active/completed states, and counter tasks auto-complete "as soon as the value and the counter are the same". Godot Questify objective nodes complete only when all attached conditions are true — [Game Creator: Quests Tasks](https://docs.gamecreator.io/quests/quests/tasks/), [Questify for Godot 4](https://docsearch.algolia.com/mcp/docs/repo/thewalruzz/godot-questify)

### Inferences
- Quest Machine's model translates directly into Rust enums: `NodeKind { Start, Condition, Passthrough, Success, Failure }`, `NodeState { Inactive, Active, Satisfied }`, `QuestState { NotStarted, Active, Succeeded, Failed, Abandoned, Disabled }`, `ConditionSet { mode: Any|All|Min(n), conditions }`. `ParentQuestCondition` with Min(n) generalises "prerequisites as a DAG" to k-of-n joins.
- The DataSync vs Messages counter modes are the event-delta vs state-query split noted under Unreal. A Rust core should support both: `Counter::Accumulate(event filter)` and `Counter::Observe(query key)`, where the host supplies the queried value.
- The separate "minimum data" serializer confirms the definitions-vs-progress split. Per-save data is node states, counter values and condition-set state, keyed by stable IDs, while authored quest assets stay static.

- The official Quest Machine and Dialogue System manuals did not load. The full Dialogue System state list (unassigned/active/success/failure/abandoned/grantable/returnToNPC, from memory) is unverified.
- No specific source found on ScriptableObject-based quest data or on Unity's own stats/achievements service patterns.

## Narrative tools and shipped-game talks: articy:draft, Yarn Spinner, ink, Horizon Zero Dawn, Witcher 3

### Takeaway
Narrative tools store quest state as flat, namespaced, typed global variables: articy has bool/int/string in variable sets, Yarn Spinner has a pluggable VariableStorage, and The Witcher 3 has a numeric Facts DB. Expressions read them (conditions) and write them (instructions). Horizon Zero Dawn built quests as graphs of steps, each bound to a verb + target + count from a finite verb list. It enabled ~150 quests and auto-generated player fetch jobs, but could not "un-happen" steps.

### Cited Findings
- Horizon Zero Dawn (GDC 2017, Leszek Szczepański) places quest systems on a scale. **Relaxed** systems have no central system, no defined quest concept, and all logic in scripts (examples: Might & Magic, RPG Maker). **Strict** systems use one central system and rigid predefined elements without scripting (Titan Quest, Sacred). Witcher 2, Skyrim and HZD sit in the middle — [Guerrilla GDC 2017 slides (PDF)](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf)
- HZD model: "A quest is represented as a graph of steps." Only start steps are initially available. "Completing a step … opens or closes parts of the graph." The quest ends when an end step is reached. It was inspired by the writers' "Wall of Sticky Notes" (notes are plot points, lines are cause and effect) — [Guerrilla slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf)
- HZD progression: "Each step is connected to a verb which defines the action the player needs to perform … and if necessary the target." There is "a finite amount of verbs … for example: obtain, kill, converse". Examples are `Obtain | Amulet of Yendor` and `Kill | Gladiator | 6` — [Guerrilla slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf)
- HZD results: "almost 150 quests". The strict verb set allowed automated generation of player-created fetch quests ("Player jobs"). Problems were the "Time travel problem" (steps could not be reverted when gameplay needed to undo quest state, because of the story metaphor) and a verb list that "didn't sufficiently match our needs" — [Guerrilla slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf); talk page: [GDC Vault](https://gdcvault.com/play/1024158/Building-Non-linear-Narratives-in)
- The Witcher 3 (REDkit docs): the **Facts DataBase** is "a system that many quests and other systems depend on", made of named variables with number values. Scripts or the "FactsDB Change" quest block add and change facts, and quest, scene and script conditions check them. Facts can be set to **expire** after a time period. The Quests Debugger shows questlines for the last loaded save, highlights "currently active signals" in node graphs, and can "continue from" a node — [CD Projekt RED REDkit wiki: Quests Debugger](https://cdprojektred.atlassian.net/wiki/spaces/W3REDkit/pages/6328642/TOOL+Quests+Debbuger)
- articy:draft: global variables live in **variable sets** (namespaces), referenced as `VariableSet.Variable`. Types are Boolean, Integer and String, each with a description and default value. articy:expresso **conditions** test values to steer flow and **instructions** modify them. A simulation mode tests scripts — [articy Help: Global Variables](https://www.articy.com/help/Scripting_GlobalVariables.html), [articy Help: Scripting](https://www.articy.com/help/Scripting_in_articy.html), [articy: scripting basics](https://www.articy.com/en/adx_basics_scripting/)
- The articy Unity importer generates a `GlobalVariableStorage` class from project data, with a `NamespaceVariableMap` grouping by namespace — [articy Unity importer API](https://www.articy.com/articy-importer/unity/html/T_Articy_Unity_BaseGlobalVariables.htm)
- Yarn Spinner: storage is pluggable through a `VariableStorage` trait in the Bevy port. The default `MemoryVariableStorage` is erased when the game stops. "Yarn Spinner makes no assumptions about how variables are saved"; custom storage is passed with `DialogueRunnerBuilder::with_variable_storage` — [Yarn Spinner for Bevy: Variable Storage](https://docs.yarnspinner.dev/yarn-spinner-for-other-engines/bevy/components/variable-storage); Unity counterpart: [Yarn Spinner: Variable Storage](https://docs.yarnspinner.dev/components/variable-storage/variable-storage)
- ink: save by serialising the whole story state (`story.state.ToJson()` / `LoadJson()` before `Continue()`), and restore against the same compiled `.ink.json` version — [Bugnet blog](https://bugnet.io/blog/how-to-fix-ink-story-choices-not-persisting-across-save) (secondary source)

### Inferences
- A shared "blackboard" of namespaced typed facts (bool/int/string, optionally with expiry) is the lowest common denominator across articy, Yarn, ink and Witcher. A Rust core that exposes facts behind a trait, as Yarn's `VariableStorage` does, lets dialogue (for example Yarn Spinner for Bevy) and quest conditions read the same store, and makes save/load one map.
- HZD's verb + target + count is a strong default for a data-driven objective. A *closed but extensible* verb enum (or tag) keeps quests quick to author and enables procedural generation, as HZD's player jobs did. Its stated regrets argue for (a) an extensible verb set and (b) explicitly modelled reversible objectives: for example "hold 6 items" as a state query that can drop back to incomplete, as opposed to latched "obtained" events.
- Witcher's fact expiry and the debugger's "continue from node" point to tooling to build in: time-bounded facts on a sample/game clock, and a debug API to force node states.
- ink's "same compiled version" warning is the versioning hazard for any definitions-vs-progress split. Save files should carry a definitions version or content hash and stable IDs, plus a migration path for renamed or removed nodes.

- No GDC/Ubisoft "objective tracker" talk primary source retrieved. Paweł Sasko's Witcher 3/Cyberpunk talk is referenced only by secondary coverage ([GameBanshee](https://www.gamebanshee.com/943k6)), with no architecture detail.

- ink's native variable-observer API was not confirmed by a primary source.

## Event-sourcing vs state machines; counters, idempotence, prerequisites, save/load, determinism

### Takeaway
Shipped systems are overwhelmingly **state machines over a graph** (node states plus counters), fed by events. A few are event-log based: Quest Extension's "Memories" and Witcher's fact store. The primary sources found contain no explicit event-sourcing writeups for quests; the recommendations below are inferences from the cited models.

### Cited Findings
- Graph + node-state machine: Quest Machine (Inactive → Active → True, with node types driving transitions) — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html). HZD step graph opening and closing steps — [Guerrilla slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf)
- Event-log flavour: Quest Extension records world events through time ("Memories") and completes quests from them — [Quest Extension listing](https://www.unrealengine.com/marketplace/content/c47dc67dda684ee6b3685c64c8008428)
- Monotonic progress and idempotence: platform achievements reject non-increasing updates — [Epic Achievements Interface](https://dev.epicgames.com/documentation/en-us/unreal-engine/online-subsystem-achievements-interface-in-unreal-engine)
- Prerequisites as joins: `ParentQuestCondition` ("enough parent nodes are true") plus cross-quest `QuestStateQuestCondition` — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Minimal progress serialisation separate from definitions — [Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)
- Reversal is a known pain point ("Time travel problem") — [Guerrilla slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf)

### Inferences
- Recommended hybrid for a pure-Rust core: a **pure reducer** `fn apply(defs: &Defs, progress: &mut Progress, event: &Event) -> Vec<Outcome>`, deterministic with no clock, RNG or I/O. Time arrives as an event or tick carrying a game or sample time.
  - Progress is a snapshot (node states plus counters) rather than a full log. This keeps saves small, as with Quest Machine's minimal serializer.
  - An optional bounded event journal can serve replay and tests.
- Idempotent completion: transitions to terminal states are latched and emit an `Outcome::Completed` exactly once. Counters clamp at target. Re-applying a "complete" or a duplicate event is a no-op. Monotonic `max` merges suit achievement-like stats.
- Testability: because the reducer is pure, tests are tables of `(defs, events) → expected outcomes/progress`, with no Bevy app. This fits the repo's existing "render offline, assert" testing culture.
- Prerequisites: validate the definition graph at load (no cycles unless explicitly looping; all referenced IDs exist; reachable end nodes). Mirrors `openspec validate --strict` discipline.
- Support both latched objectives (events: "obtained", "killed") and live objectives (state queries: "has N", "light quality ≥ x"). Live ones are re-evaluated when the host reports changed facts. This addresses both HZD's reversal problem and Narrative's "already had items" edge case.

### Gaps
- No primary source found that benchmarks event-sourced vs snapshot quest progress in a shipped game.

## Rust / Bevy ecosystem

### Takeaway
There is no mature, maintained Bevy quest or objective crate. `micro_quest` (2023, Bevy 0.10) has an optional Bevy feature over a pure data core, and `bevy_goals` is a tiny 2-commit, 0-star plugin with Bevy-coupled conditions and events. `iyes_progress` tracks progress only for state transitions. The pattern most worth copying is micro_quest's: a pure core plus a `bevy` cargo feature or a separate adapter crate. Persistence can use moonshine-save (Reflect + `Save` marker, observer-triggered), or the core's own serde types serialised directly.

### Cited Findings
- `micro_quest` 0.1.0 (only release, 2023-04-26) provides "data and systems for structuring quests and dialogue". It reads `.quest` TOML files produced by the Micro Forge editor. With the `bevy` feature it adds a `QuestLog` resource, a `.quest` asset loader, and an asset-server ID locator. The bevy feature pins `^0.10.1` — [docs.rs micro_quest](https://docs.rs/crate/micro_quest/latest), [lib.rs micro_quest](https://www.lib.rs/crates/micro_quest), [lib.rs features](https://lib.rs/crates/micro_quest/features)
- `bevy_goals` (ChrisTutorials, GitHub) has `Goal` (id, description, conditions) in a `GoalRegistry` resource, plus `Milestone` / `MilestoneRegistry`. Conditions are Threshold, CounterThreshold, Flag, All, Any, Always and Never. A `GoalTracker` trait provides `progress() -> 0..1` and `is_complete()`. `GoalMetEvent { goal_id, tick }` and `MilestoneReachedEvent` are read through `EventReader`. Its design keeps "continuous simulation" running after goals are met. It has 2 commits, 0 stars, MIT licence, and no persistence or Bevy version stated — [GitHub bevy-goals](https://github.com/ChrisTutorials/bevy-goals)
- `iyes_progress` is a Bevy plugin "to help track progress and perform state transitions", mainly loading screens — [GitHub iyes_progress](https://github.com/IyesGames/iyes_progress), [docs.rs 0.16](https://docs.rs/crate/iyes_progress/latest/source/src/lib.rs)
- `bevy_ios_gamecenter` wraps Apple GameKit achievements (iOS only) — [crates.io](https://crates.io/crates/bevy_ios_gamecenter)
- moonshine-save: the `Save` marker component marks a whole entity (usable with `#[require(Save)]`). Saved components must derive `Reflect`, use `#[reflect(Component)]`, and be registered. Components holding entities need `MapEntities`. The current API uses observers (`save_on_default_event`, `load_on_default_event`) triggered by save/load events; older 0.1.x used `save_into_file` systems. docs.rs showed 0.6.1 as latest at search time; its Bevy 0.20 compatibility is unconfirmed — [docs.rs moonshine-save](https://docs.rs/crate/moonshine-save/latest), [army.rs example](https://docs.rs/crate/moonshine-save/latest/source/examples/army.rs)
- Yarn Spinner has an official Bevy port with a trait-based `VariableStorage`, a candidate shared fact store for dialogue and quests — [Yarn Spinner for Bevy](https://docs.yarnspinner.dev/yarn-spinner-for-other-engines/bevy/components/variable-storage)
- Veloren (Rust voxel RPG): its wiki main page once listed a "quest system" as planned for 0.9. Later releases (0.15) added a reputation/crime memory system and a world boss. No source found documenting a shipped Veloren quest architecture — [Veloren wiki](https://wiki.veloren.net/wiki/Main_Page), [GamingOnLinux 0.15](https://gamingonlinux.com/2023/07/multiplayer-voxel-rpg-veloren-v015-is-out-adding-the-first-world-boss)

### Inferences
- Recommended crate shape, aligned with the repo's existing `stubby_recipes` rule (no Bevy):
  - `stubby_goals` (or an extension of `stubby_recipes`) holds serde `Defs` (RON/JSON/TOML in `assets/`), `Progress` (serde, stable string/u32 IDs), a `FactStore` trait, `Event` (verb tag, target tag(s), magnitude, time), and a pure `apply` / `evaluate`.
  - A thin adapter in `stubby_game` wraps `Progress` in a `Resource`, converts Bevy messages and observers (pickup, harvest, patch-connected, light-quality changed) into core `Event`s, and re-emits `Outcome`s as Bevy messages for HUD and recipe-book UI.
- Persistence: either serialise `Progress` directly with serde (simplest, keeps the core engine-agnostic), or wrap it in a Reflect resource for moonshine-save. The core should never need Reflect; the adapter can provide a newtype.
- Mapping to this game: "discover a square wave", "harvest N reeds" and "patch clock GATE → VCA TRIG" are HZD-style verb/target/count objectives (`Collect square_wave 1`, `Harvest reed 6`, `Connect gate→trig`). "Bloom a scrub oak" or "light quality ≥ x in region" are live state-query objectives. Per the project's "simulator, not levels" stance, use open-ended milestones (bevy_goals' "continuous simulation" idea) rather than terminal quest endings.

- No Bevy Discord summaries, Bevy Assets page entries or jam-game writeups on quest architecture were found in this pass. Fish Folk and Tiny Glade quest/progress structure was not researched (no sources surfaced).
- Bevy 0.20-specific API names for messages and observers were not verified against primary docs in this pass.
