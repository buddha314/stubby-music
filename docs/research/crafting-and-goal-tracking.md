# Engineers own the schema, designers own rows

*Research, 2026-11-01. Sourced notes behind this report: `crafting-and-goal-tracking/`. Acted on in `add-rules-data-conventions` and `add-inventory-and-goals-hud`.*

Every long-lived systemic game in this survey enters its rules the same way: **engineers define a typed schema and the code that interprets it, designers fill in rows of declarative data, and a validator checks the rows before the game runs**. Unreal's Data Tables, RimWorld's XML Defs, Minecraft's data packs, Factorio's prototypes and Satisfactory's recipe and schematic assets all follow this pattern. Where they differ is in how strict the validator is and how they handle IDs and renames. The tracking side is just as consistent. Shipped factory and crafting games keep **immutable definitions** (recipes, unlocks, milestones) apart from a **small, mutable save state** keyed by stable string IDs: completed flags, per-item paid-off amounts, counters and pinned recipes. Availability ("what can I do now") is recomputed from the definitions rather than stored. For stubby-music the answer is mostly confirmation. The repo already has JSON in git, a Bevy-free validator crate, and OpenSpec for rule *types*, which is the strongest-evidenced setup for a small team. The gaps are strictness, a few conventions, and a few data-model decisions. The validator should reject unknown fields. IDs should be treated as save-game API with a rename-migration table. Data should be split per domain. Validation should be layered into shape, semantics and simulation. The goals design should adopt Satisfactory-style per-goal partial payment and a pure, snapshot-based progress reducer. The rest of the merged `add-inventory-and-goals-hud` design matches shipped practice and should stand.

## Rules reach the build as data rows inside code-owned schemas

The canonical statement comes from Unreal's own documentation. Designers keep balance data in Excel workbooks whose macro buttons export CSV, which is reimported as a Data Table. Changes then apply "without code changes", but only after **"a programmer has to create the row container telling the engine how to interpret the data"** ([Unreal: Data Driven Gameplay Elements](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine)). The first CSV column must be `Name`, the lookup key. The importer has `Ignore Extra Fields` and `Ignore Missing Fields` flags that decide whether a mismatch between schema and sheet warns or passes silently. RimWorld puts the same split in text: each XML `<Def>` must match a C# type, so code owns the schema while content lives in a mod's `Defs` folder, templated from the vanilla Defs ([RimWorld Wiki: XML file structure](https://rimworldwiki.com/wiki/Modding_Tutorials/XML_file_structure); [Defs](https://rimworldwiki.com/wiki/Modding_Tutorials/Defs)). Minecraft makes the **file path the ID**. A file at `data/<namespace>/<registry>/<path>.json` becomes `<namespace>:<path>`, and namespaces exist "to avoid files from different packs unintentionally interfering with each other" ([Minecraft Wiki: Data pack](https://minecraft.wiki/w/Data_pack)).

Spreadsheets remain a mainstream front end for this data. At GDC 2026's Spreadsheets Microtalks, Epic Tavern described building game data directly from Google Sheets, and *Darkwater*'s team described an economy sheet that simulates its procedurally generated loot and districts before the data ships ([GDC Vault: Spreadsheets Microtalks](https://gdcvault.com/play/1035719/Spreadsheets)). The sheet has a cost: it becomes a second copy that can drift from the build, and nothing proves the two agree unless someone reimports. CastleDB, Nicolas Cannasse's "structured static database", was built to avoid that. It keeps spreadsheet-style typed columns, but the edited artifact *is* human-readable JSON holding both schema and rows, so git can diff and merge it ([lib.haxe.org: castle](https://lib.haxe.org/p/castle); [dbdb.io](https://dbdb.io/db/castledb/revisions/3)). *Inference:* stubby-music already sits at CastleDB's end of this spectrum, with `catalog.json` as the single source in git. A spreadsheet front end would add a drift problem the project does not currently have.

Recipes and unlocks are kept as **separate objects**, and the unlock refers to the recipe by ID. In Satisfactory a `Recipe_*` asset (`FGRecipe`) holds an ingredients array, a products array, the machines it is "Produced In" and a duration. A `Schematic_*` asset (`FGSchematic`) holds a type, an item cost and an `Unlocks` list that contains, for example, a `BP Unlock Recipe` pointing at a recipe asset ([ficsit.app: Recipe vs Schematic](https://docs.ficsit.app/satisfactory-modding/latest/Development/BeginnersGuide/SimpleMod/recipe.html)). Minecraft does the same: a recipe JSON says what can be made, and a separate advancement JSON with `rewards.recipes` says when the player learns it ([minecraft.wiki: Advancement definition](https://minecraft.wiki/w/Advancement_definition)). Factorio stages the split through its load lifecycle. All prototype data is defined in Lua during a data stage of three rounds across every mod (`data.lua`, `data-updates.lua`, `data-final-fixes.lua`). The state is then discarded, and at runtime "prototypes can no longer be modified" ([Factorio: Data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)). On the modding side, Fabric's datagen generates recipe and advancement JSON from typed code, so the shipped JSON is a reviewed build artifact whose source is type-checked ([Fabric docs](https://docs.fabricmc.net/develop/data-generation/setup)).

Process conventions follow from the file format. Binary assets cannot be merged, so studios lock them and split monolithic files by function to reduce contention ([GIGAZINE on Kurilin's "Why Game Devs Don't Merge Files"](https://www.gigazine.net/gsc_news/en/20260619-game-dev-dont-merge-files)). Even text merge tools fail when two people edit the same object, as UnityYAMLMerge does ([Diversion blog](https://diversion.dev/blog/resolving-conflicts-in-game-development-projects)). Paradox modders get live validation of script data in VS Code through CWTools, which moves the engine's `error.log` messages ("Malformed token: 95, near line: 4") into the editor ([Paradox forum: CWTools](https://admin-forum.paradoxplaza.com/forum/threads/tool-cwtools-a-mod-validating-extension-for-vs-code.1066033)). The notes found **no primary source** on formal PR review of data at large studios, on live-ops content-only patch practice, or on indie tooling budgets. The small-team recommendations below extrapolate from the larger systems.

## Lenient loaders fail in five documented ways

Most of what goes wrong with data-driven rules is data the loader accepted but should not have. **Factorio ignores unrecognized properties**, so a misspelled field silently does nothing. It does error on missing required ones and names the missing property ([Factorio: Data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)). Unreal's "ignore" import flags give the same silence by choice. **Well-formed but semantically invalid data** is the second failure. A Satisfactory recipe quantity above the item's stack size means the machine never runs, and the asset format cannot express that constraint ([ficsit.app](https://docs.ficsit.app/satisfactory-modding/latest/Development/BeginnersGuide/SimpleMod/recipe.html)). **Invisible content** is the third. A Satisfactory schematic does not exist in game until it is registered in the root Game World Module's `M Schematics` array (same source). **Inheritance and load-order surprises** are the fourth. In RimWorld an incomplete abstract parent "will crash the game", `abstract` is not `Abstract`, lists append while scalars overwrite, and redefining core abstracts "is common cause for mod compatibility issues" ([RimWorld XML file structure](https://rimworldwiki.com/wiki/Modding_Tutorials/XML_file_structure)). Dwarf Fortress sets raw load order by each file's first line, and duplicated raws "can cause strange, difficult-to-diagnose problems, and even crashes" ([DF Wiki: Raw](https://dwarffortresswiki.org/index.php/DF2014:Raw)). **Renames that silently drop progress** are the fifth and most relevant to saves. Minecraft keys advancement progress by ID, so when files were renamed in 1.16-pre1 "progress in this advancement is not kept" ([minecraft.wiki: Advancement](https://minecraft.wiki/w/Advancement)).

The shipped mitigations map one to one onto those failures. Minecraft's loader became "strict JSON" in 17w18a. A failed `/reload` keeps the previous data ("changes are not applied and the game continues using previous data"), and `pack.mcmeta` declares an explicit data-format version range ([Minecraft Wiki: Data pack](https://minecraft.wiki/w/Data_pack); [Advancement](https://minecraft.wiki/w/Advancement)). Factorio handles renames with **once-only migrations**: "saves will remember the file names of the migrations that have already been applied to it". JSON rename migrations run before Lua migrations that have full game-state access ([Factorio: Data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)). Satisfactory keeps deprecated fields in its save structs purely for compatibility. `AFGGamePhaseManager` still carries the old `mGamePhase` enum and `mGamePhaseCosts` beside their replacements ([SML FGGamePhaseManager.h](https://raw.githubusercontent.com/satisfactorymodding/SatisfactoryModLoader/master/Source/FactoryGame/Public/FGGamePhaseManager.h)). Valheim gates each newer save field behind `if (version >= N)` ([valheim-save-tools PlayerData.java](https://github.com/Kakoen/valheim-save-tools/blob/master/valheim-save-tools-lib/src/main/java/net/kakoen/valheim/save/archive/character/PlayerData.java)).

*Inference:* the five conventions that survive across these systems are as follows. First, a stable string ID distinct from the display name. Second, a schema owned by code that rejects unknown fields. Third, a semantic validator that reports file, entry and field. Fourth, atomic hot reload that keeps the old data on failure. Fifth, explicit rename migrations recorded in the save. Lenient loading suits mod ecosystems where many independent packs must coexist. A single-designer game has no such constraint, so strictness costs it nothing.

## Shipped games store small progress and derive availability

The data model has converged. **Definitions are immutable; per-save progress is minimal and keyed by ID; "what is available now" is computed.** Satisfactory's `AFGSchematicManager` saves exactly three things: purchased schematic classes, the one active schematic, and `mPaidOffSchematic`, an array of `FSchematicCost { Schematic, ItemCost }` whose comment reads "This keeps track of what players have paid off on different schematics". The list of all schematics is rebuilt at startup and not saved ([SML FGSchematicManager.h](https://raw.githubusercontent.com/satisfactorymodding/SatisfactoryModLoader/master/Source/FactoryGame/Public/FGSchematicManager.h)). Because partial payment is stored **per schematic**, a player who switches the active milestone keeps what they paid toward the old one. The Space Elevator repeats the shape with `mCurrentGamePhase`, `mTargetGamePhase` and `mTargetGamePhasePaidOffCosts`. Its `PayOffOnTargetGamePhase` returns the amount accepted, and `GetRemainingPhaseCosts` returns total and remaining per item (same header family, [FGGamePhaseManager.h](https://raw.githubusercontent.com/satisfactorymodding/SatisfactoryModLoader/master/Source/FactoryGame/Public/FGGamePhaseManager.h)). Mindustry's `TechNode` keeps a `finishedRequirements` array parallel to its item `requirements` and persists each element under a settings key `req-<content>-<item>` ([TechTree.java](https://raw.githubusercontent.com/Anuken/Mindustry/master/core/src/mindustry/content/TechTree.java)). Stardew's Community Center bundles store per-slot (item, count, quality) requirements, so partial donations survive ([rdew docs citing the Stardew wiki](https://rdrr.io/github/aftonsteps/rdew/man/bundles.html)).

Satisfactory's dependencies are **polymorphic instanced objects**, not tiers. A schematic's `mSchematicDependencies` holds entries such as `BPSchematicPurchasedDependency` and `BPItemPickedUpDependency`, each group with a Require-All toggle. Flags such as `mHiddenUntilDependenciesMet` control visibility ([SML FGSchematic.h](https://raw.githubusercontent.com/satisfactorymodding/SatisfactoryModLoader/master/Source/FactoryGame/Public/FGSchematic.h); [docs.ficsit.app Schematic](https://docs.ficsit.app/satisfactory-modding/latest/Development/Satisfactory/Schematic.html)). Unlocks are a closed list of types: recipe, schematic, inventory slot, give item, map, scannable resource, build efficiency, overclock and subsystem. The pinned to-do list lives on the player state: `mPrivateTodoList` as free text, plus an `mShoppingListComponent` of pinned recipe entries. Notably, there is a `GetAndClearShoppingListForMigration()` hook ([SML FGPlayerState.h](https://raw.githubusercontent.com/satisfactorymodding/SatisfactoryModLoader/master/Source/FactoryGame/Public/FGPlayerState.h)). Pins are recipes, not goals, and the remaining totals are computed in the UI.

Across games, three accounting modes recur, and they behave differently enough that the choice is a design decision, not an implementation detail.

| Mode | Shipped examples | What is saved | Trade-off |
| ---- | ---------------- | ------------- | --------- |
| Deliver and consume into a sink | Satisfactory HUB and Space Elevator; Shapez 2 Vortex; Factorio labs | Paid-off amount per item per goal | Cannot double-count; acts as a resource sink; needs a hand-in point |
| Cumulative produced or built counter | Factorio `craft-item` triggers and flow statistics; Mindustry `placedBlockCount` | A global ledger keyed by item ID | Rewards building chains; "produced" needs a careful definition |
| Held snapshot | Mindustry `ItemObjective`; Satisfactory item-picked-up dependency | Nothing (polled) | Cheap; can be met and then lost; suits first-discovery gates |

Sources: [Shapez 2 wiki: Vortex](https://shapez2.wiki.gg/wiki/Vortex); [Factorio TechnologyTrigger](https://lua-api.factorio.com/latest/types/TechnologyTrigger.html); [LuaFlowStatistics](https://lua-api.factorio.com/latest/classes/LuaFlowStatistics.html); [Mindustry MapObjectives.java](https://raw.githubusercontent.com/Anuken/Mindustry/master/core/src/mindustry/game/MapObjectives.java).

Factorio 2.0 shows both cost-based and event-based goals in one schema. A technology has **either** a `unit` (science-pack cost) **or** a single `research_trigger` of type `craft-item`, `mine-entity`, `build-entity`, `send-item-to-orbit`, `scripted` and others. Per-technology progress is a single `saved_progress` fraction in [0, 1) ([TechnologyPrototype](https://lua-api.factorio.com/latest/prototypes/TechnologyPrototype.html); [LuaTechnology](https://lua-api.factorio.com/latest/classes/LuaTechnology.html)). The trigger design has known rough edges. `mine-entity` also fires on side-effect collection ([forum bug report](https://forums.factorio.com/viewtopic.php?p=655779)). Modders asked for more than one trigger per technology ([forum](https://forums.factorio.com/viewtopic.php?p=649378)). Some players found arbitrary craft counts odd ([FFF #376 thread](https://forums.factorio.com/viewtopic.php?p=591287)). Shapez 2 turns its sink into open-ended progression. Every milestone from "Fluids & Painting" onward unlocks a goal line whose required counts grow exponentially, and each line level raises a single Operator Level ([Shapez 2 wiki: Operator Level](https://shapez2.wiki.gg/wiki/Operator_Level)). That model fits a game with no ending.

## Discovery is a flag, goals are criteria, and listeners do the work

Discovery-style unlocks are stored as **sets of known IDs that never revert**. Valheim's character file holds `knownRecipes`, `knownMaterials` and `knownStations` (with station level), plus known biomes and texts ([valheim-save-tools](https://github.com/Kakoen/valheim-save-tools/blob/master/valheim-save-tools-lib/src/main/java/net/kakoen/valheim/save/archive/character/PlayerData.java)). In code, a piece counts as "known" when its station and every material name are in those sets ([aedenthorn CraftFromContainers](https://github.com/aedenthorn/ValheimMods/blob/main/CraftFromContainers/BepInExPlugin.cs)). *Inference:* this is **derived knowledge**. Only primitive discoveries are stored, so a recipe added in a later patch becomes known automatically for a player who already has its inputs, and nothing needs migrating. Minecraft writes the same idiom out per recipe. Vanilla `recipes/tools/iron_pickaxe` grants the recipe when the player holds an iron tool material **or** already knows the recipe; the second branch makes it idempotent ([misode/mcmeta](https://github.com/misode/mcmeta/tree/data/data/minecraft/advancement/recipes)). Subnautica adds threshold discovery. A scanner entry unlocks a blueprint after `totalFragmentsRequired` scans, and partial counts are saved state ([Nautilus PDAHandler](https://subnauticamodding.github.io/Nautilus/api/Nautilus.Handlers.PDAHandler.html); [Steam discussion](https://steamcommunity.com/app/264710/discussions/0/2333276539607034660)).

Goal definitions reduce to a few primitives: **typed triggers, criteria (a trigger plus a predicate), combinators, and rewards**. A Minecraft advancement has named criteria, and its `requirements` list is an AND of ORs: it "is granted when every inner list has at least one completed criterion". Rewards are recipes, loot, experience or a function ([minecraft.wiki: Advancement definition](https://minecraft.wiki/w/Advancement_definition)). Pixel Crushers' Quest Machine is the most fully specified commercial model. It has node types Start, Condition, Passthrough, Success and Failure. Each node has a state of Inactive, Active or True. Condition sets combine with Any, All or Min(n), and counters are updated either by messages or by `DataSync` from game state. A separate `QuestStateSerializer` "serializes the minimum data needed for design-time quests" ([Quest Machine API](https://www.pixelcrushers.com/quest_machine/api/html/namespace_pixel_crushers_1_1_quest_machine.html)). Horizon Zero Dawn bound each quest step to **one verb from a finite list plus a target and count**, as in `Kill | Gladiator | 6`. That shipped almost 150 quests and allowed auto-generated player jobs. The team regretted two things: steps could not be "un-happened" (the "Time travel problem"), and the verb list "didn't sufficiently match our needs" ([Guerrilla GDC 2017 slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_Szczepanski_BuildingNonLinearNarrativesInHorizonZeroDawn.pdf)).

Evaluation is mostly **event-driven, with listeners removed on completion**. Minecraft's `SimpleCriterionTrigger` keeps a map from each player to that player's listeners for unfinished criteria and tests only those on each event ([mappings.dev SimpleCriterionTrigger](https://mappings.dev/1.21.11/net/minecraft/advancements/criterion/SimpleCriterionTrigger.html)). Mindustry instead polls each map objective every frame, but only once it is "qualified", meaning all its parents are complete ([MapObjectives.java](https://raw.githubusercontent.com/Anuken/Mindustry/master/core/src/mindustry/game/MapObjectives.java)). The Narrative plugin for Unreal records a lesson about mixing the two. A task activated late must count items the player *already holds*, or it waits for new events that may never arrive ([Versluis](https://www.versluis.com/2025/08/creating-custom-tasks-for-quests-in-narrative-tales/)). Platform achievement APIs add a monotonic rule: "Many services reject updates that do not raise a player's existing percentage" ([Epic: Achievements Interface](https://dev.epicgames.com/documentation/en-us/unreal-engine/online-subsystem-achievements-interface-in-unreal-engine)). On event sourcing versus held state, the notes found **no shipped game that event-sources quest progress**. The Quest Extension plugin's "Memories" log and The Witcher 3's numeric, optionally expiring Facts DB are the closest log-like designs ([Quest Extension](https://www.unrealengine.com/marketplace/content/c47dc67dda684ee6b3685c64c8008428); [REDkit Quests Debugger](https://cdprojektred.atlassian.net/wiki/spaces/W3REDkit/pages/6328642/TOOL+Quests+Debbuger)). Everything else stores snapshots.

The Rust ecosystem offers nothing to adopt wholesale. `micro_quest` had a single 2023 release pinned to Bevy 0.10 ([lib.rs](https://www.lib.rs/crates/micro_quest)). `bevy_goals` has 2 commits and no persistence ([GitHub](https://github.com/ChrisTutorials/bevy-goals)). The pattern worth copying from `micro_quest` is a pure data core with Bevy behind a feature or adapter, which is already the repo's `stubby_recipes` rule.

## Recommended conventions and design changes for stubby-music

Everything in this section is *inference* from the evidence above, applied to the current repo. At `origin/main`, `catalog.json` holds three items, three resources, two mines and no recipes. `stubby_recipes` derives `Deserialize` without `deny_unknown_fields`, and it reports errors as `RecipeError::InvalidCatalog(String)`. IDs must be unique per registry and are checked against `[A-Za-z0-9_-]`. The item `clock` and the resource `clock` share an ID across two registries.

### Authoring conventions to adopt

The central convention is the Unreal and RimWorld split, translated to this team. **The designer (the human) owns rows. Codex owns the schema and interpreter in `stubby_recipes`. OpenSpec owns the rule types and invariants.** That gives two distinct change flows, and the PR template should ask which one a change is. A **new data row** of an existing type uses the first flow: a recipe, a goal, a yield quantity, a replenishment interval. It is a data-only PR touching `assets/recipes/*.json` and needs no OpenSpec change, because the spec states invariants, not values. It passes `cargo test -p stubby_recipes`, and anyone may open it, including Claude for art-adjacent rows such as icons. A **new rule type** uses the second flow: a new trigger kind, a new unlock kind, a new accounting mode, a new field. It needs an OpenSpec change with SHALL requirements and scenarios, then Codex's schema and validator code, then example rows. HZD's regret about a closed verb list is cheap to fix here, because adding a rule type is one agent PR, not a studio escalation. Rows should never grow logic; no expression mini-language belongs in JSON.

| Convention | Rule | Why (source pattern) |
| ---------- | ---- | -------------------- |
| File layout | Split by domain: `assets/recipes/{items,resources,mines,recipes,goals}.json`, loaded and cross-validated together; or keep one `catalog.json` but add `goals.json` beside it and split once parallel edits conflict | Splitting by function to cut contention ([Kurilin via GIGAZINE](https://www.gigazine.net/gsc_news/en/20260619-game-dev-dont-merge-files)) |
| Formatting | One object per array entry, sorted by `id`, canonical `serde_json` pretty print; CI fails on unformatted files | Line-level diffs stay one row per change |
| IDs | `snake_case` ASCII `[a-z0-9_]`, never reused, distinct from `name`; tighten the current check (it allows uppercase and `-`); one ID namespace across registries, or prefixed references (`item:clock`) where two registries can collide | Minecraft namespaced IDs; Unreal `Name` key |
| IDs as save API | Renaming or removing an ID requires a row in `assets/recipes/migrations.json` (`{"from": "...", "to": "..." \| null}`); saves record applied migrations | Factorio once-only rename migrations; Minecraft 1.16 progress loss |
| Shape validation | `#[serde(deny_unknown_fields)]` on every definition struct; generate a JSON Schema from the Rust types (e.g. with `schemars`) and reference it via `$schema` for VS Code autocomplete | Factorio ignores typos; CWTools-style editor validation |
| Semantic validation | Every reference resolves; no cycles in `after`; every recipe reachable (obtainable inputs) and every unlock target exists; quantities within any stack limit; errors are structured `{file, id, field, message}` | Satisfactory stack-size stall and unregistered schematics |
| Hot reload | On a failed reload keep the previous catalog and show the error | Minecraft `/reload` |
| Data version | A top-level `"format": N` in each file; the save records the content format it was written against | Minecraft `pack_format`; ink's same-version warning |

Testing should come in three layers. The first is a test that loads the **real shipped files** (not fixtures) and runs every validator. That test exists in spirit and should be explicit. The second is golden tests for canonical rows, for example "a `lightning_bug` yields 2 `square_wave`" and "the first goal is reachable from the opening's resources". The third is a small **seeded economy simulation** that replays N in-game nights of collection under the replenishment policies and asserts that every authored goal can be completed within a bound. This is the code version of *Darkwater*'s simulating spreadsheet, and the project's deterministic-seed rule makes it practical.

### What to change or confirm in `add-inventory-and-goals-hud`

Most of the merged design matches shipped practice and should be confirmed. Its strongest choices are D1 (goals as item lists in two horizons), D2 (prerequisites through `after` instead of a tier concept), D4 (unlocks feed a recipe book that persists at zero, the Valheim and Minecraft flag model), D5 (pins as recipe counts with totals computed in the UI, exactly Satisfactory's shopping list) and "goals never end", which Shapez 2's endless goal lines show can still carry long-term motivation. Load-time rejection of unknown items, unknown goals and cycles also stands. It is the semantic layer above.

The one substantive change is to **delivery semantics**. D3 makes delivery all-or-nothing, so the player must hold the full `requires` at once. Satisfactory, Mindustry and Stardew all persist **per-item partial payment per goal** (`mPaidOffSchematic`, `finishedRequirements`, bundle slots). Their reason is that deep goals exceed what a player can conveniently hold at once, and that switching the active goal must not lose contributions. The recommendation is to add `paid: BTreeMap<GoalId, BTreeMap<ItemId, u32>>` to `GoalProgress`. `deliver` would then accept up to the remaining amount for each item, consume exactly that through the shared transaction path, and complete the goal when nothing remains. Each delivery call stays atomic; what changes is that a goal fills over several calls. The spec's "Short delivery" scenario would change from "nothing is consumed" to "the held items are accepted, the rest stays required". If the designer wants all-or-nothing for short-term goals specifically, that can be a per-goal `delivery: all_at_once | partial` field. Note that with no inventory capacity yet the difference is small today. It grows the moment slots or capacity land, which is an open question in the design.

On **event-sourced versus held objectives**, store a snapshot. No shipped system surveyed event-sources progress, and the snapshot is what Satisfactory and Quest Machine save. Implement goal logic as a pure reducer in `stubby_recipes`, `apply(&Defs, &mut Progress, &Event) -> Vec<Outcome>`, with no clock, RNG or I/O. Tests then become tables of events and expected outcomes, and a bounded event journal can be added later for replay without changing the save. Completion should be latched and emit `Outcome::GoalCompleted` exactly once, and counters should only ever rise, so a duplicate event is a no-op. When later goal kinds arrive ("stream delivers N beats", "light quality at least x here"), give each an explicit accounting mode from the table above rather than one generic "progress". Use a Factorio-style produced/consumed ledger keyed by item ID for throughput goals. Use state queries, re-evaluated on change, for reversible conditions such as light quality, which avoids HZD's time-travel problem. Re-evaluate any newly opened goal against current state on activation, which is the Narrative plugin's late-activation lesson.

On **migrations and save shape**, the save should hold only IDs and numbers: completed goal IDs, paid-off amounts, the active choice per horizon, pins as `(recipe_id, count)`, discovered recipe-book IDs, and the content format plus applied migration IDs. Keep these as plain serde types in the core, wrapped for `moonshine-save` only in the game adapter, as task 2.9 already implies. On load, apply pending rename migrations first. Then drop progress for IDs that no longer exist, logging each one, and reopen goals whose definition changed. Satisfactory's own migration hook for the shopping list shows that pins are among the first things to need this. D5 should also say what happens when a pinned recipe disappears from the catalog; dropping the pin with feedback is the obvious answer. Two smaller confirmations remain. Pins should not be decremented by delivery, only by crafts, which the design already implies. And holding a goal's items should never complete it, which keeps square waves usable as instruments.

## Conclusion

The question of "how do we enter and maintain the rules" has a sharper answer than "use data files". Every surveyed game uses data files. What separates the robust ones is that they **refuse bad data loudly and treat IDs as a contract with every existing save**. Strictness is a mod-ecosystem cost that stubby-music does not pay, so it should take the strict end of every choice: rejecting unknown fields, tight IDs, structured errors and a recorded migration for every rename. Its unusual team shape inverts the usual trade-off. At a studio, "a new rule type needs an engineer" is the bottleneck that pushes teams toward scripting in data. Here the engineer is an agent one PR away, so the schema can stay closed and declarative, with OpenSpec serving as the gate that keeps rule types deliberate.

On tracking, the merged design is already close to Satisfactory's. Its one real gap, per-goal partial payment, is visible today only as a spec scenario but will be felt as soon as goals get deep or the inventory gets slots. The deeper implication is that a goal system for an endless simulator should be built for **change over time** rather than for completion. Definitions will be edited for years and saves must survive every edit. A small snapshot save, a pure reducer and a migration table are what make that safe.
